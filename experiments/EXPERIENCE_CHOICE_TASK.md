# Задача п.26 — влияет ли опыт на выбор определения

**Дата:** 2026-11 (сессия после п.18)
**Статус:** ЗАМЕРЕНО. Ответа «влияет» нет; найден дефект сильнее самого вопроса.
**Скрипты замера (в репозитории, `/tmp` сгорает):** `experiments/p26_measure.py`,
`experiments/p26_risk.py`. Запуск:

```bash
cd /home/tohter/LipidQwen
LIPID2_STATUS=0 .venv/bin/python experiments/p26_measure.py
LIPID2_STATUS=0 .venv/bin/python experiments/p26_risk.py
```

Оба пишут в **временный** каталог через `LIPID2_MEMORY_DIR`; живая память
сверялась sha256 до и после — `d92760c1…d767c7`, не изменилась. Учитель выключен
весь (LLM, Wiki, вопрос пользователю), чтобы ответ не зависел от сети.

## 1. Вопрос очереди и честный ответ

Очередь спрашивала: «влияет ли опыт (вес, сила перехода, сон) на то, КАКОЕ
определение выберет мозг?»

**НЕ ВЛИЯЕТ. Ни одним числом.** Это не подозрение — проверены и чтение, и
подстановка.

## 2. Карта: где вес вообще читается (полный обход)

`observation_weight` / `fact_weight` зовутся из **пяти** мест, и ни одно не
выбирает ответ:

| кто | что делает с весом |
|---|---|
| `brain/learner.py:663` | `replay_observations` — строит граф из наблюдений |
| `brain/learner.py:716,845,850,1016,1030` | пишет вес в запись наблюдения |
| `brain/lipid2_brain.py:1076` | `experience_conflicts()` — **диагноз**, не ответ |
| `brain/sleep.py:203` | сон правит `weight` и `strength` |
| `core/graph.py:215` | **единственное чтение веса ребра во всём проекте — `print_node_associations()`, то есть печать** |

`core/cortex.py:51` фиксирует это как контракт: у предиктивного цикла доступа к
`weight` нет — ни на чтение в предсказании, ни на запись.

Ответ на «что такое X» собирается в `_definition_answer()` по **жёсткому
приоритету без единого числа**:

```
definition  →  hierarchy[0]  →  properties
```

## 3. ЗАМЕР 1–2. Вес 250 против 80: ответ не шевельнулся

Сущность с двумя родителями. Первому вес 80 (пол), второму 250 (потолок, какой
даёт сон) — максимальная различимость из возможных.

```
веса наблюдений (прочитаны observation_weight):
   {'валенок|IS_A|обувь': 80, 'валенок|IS_A|кустарный предмет': 250}

вес не тронут:      Валенок — это обувь (категории: обувь -> кустарный предмет).
вес 250 у 2-го:     Валенок — это обувь (категории: обувь -> кустарный предмет).
ОТВЕТ ИЗМЕНИЛСЯ: False
```

## 4. ЗАМЕР 3–5. Свойства, определение, максимум 255

```
вес 250 на втором свойстве:  Свойства сущности 'валенок': [сшит из войлока, держит тепло].
                             (порядок — порядок записи, не вес)
вес 255 на категории + есть definition:
                             Валенок — старая русская обувь из войлока.
```

`definition` веса не имеет вовсе; категория с весом 255 ему проигрывает всегда.

## 5. ЗАМЕР 6. Ни один вариант не теряется — это хорошо

При весе 250 против 80 в ответ попали **оба** родителя (`категории: обувь ->
кустарный предмет`). То есть варианта «мнение опыта с весом 250 молча
потерялось» нет:
видно всё, просто порядок не про опыт.

## 6. ЗАМЕР 7. На что вес ВЛИЯЕТ — на диагнозе, и только

```
fact_weight(CAN_DO, conf=0.99, support=40) = 255
fact_weight(CAN_DO, conf=0.5,  support=1)  = 155

experience_conflicts() ->
  {"kind": "ontology_without_experience", "head": "валенок",
   "tail": "валять", "weight": 250, "strength": 0}
```

Единственный потребитель числа — инспектор расхождений «онтология утверждает,
опыт не подтвердил» (порог `weight >= 150 and strength <= 3`). Он работает, и
тесты на него есть. На формулировку ответа он не влияет.

## 7. ЗАМЕР 8. НАЙДЕННЫЙ ДЕФЕКТ: ответ выбирает ПОРЯДОК ЗАПИСИ в файле

Один и тот же набор фактов, записанный в разном порядке:

```
записано ['вещь',  'обувь'] : Валенок — это вещь  (категории: вещь -> обувь).
записано ['обувь', 'вещь']  : Валенок — это обувь (категории: обувь -> вещь).
ОТВЕТЫ РАЗЛИЧАЮТСЯ при ОДНОМ МНОЖЕСТВЕ фактов: True
```

**Ответ на «что такое валенок» зависит не от знания, а от того, какая строка
раньше легла в JSON.** А порядок записи — побочный эффект того, что Вики дала
категории в каком-то порядке, или Учитель ответил раньше пользователя, или
наоборот. Мозг делает валенок то «вещью», то «обувью» в зависимости от
обстоятельств, не имеющих отношения к миру.

Это ровно тот класс дефекта, с которым проект уже боролся: `_definition_answer`
в docstring прямо пишет, что `h[-1]` «оказался ближе всего к истине только
случайно» — и взял `h[0]`. Случайность не убрали, а зафиксировали место
случайности. Соседняя ветка (`_answer`) поступила иначе: строки из наблюдений
отсортированы, потому что «без сортировки одно и то же состояние давало разный
ответ».

## 8. ЗАМЕР 9. Риск, если ранжирование ввести наивным образом

```
иерархия ['обувь', 'вещь'], опыт кричит: 'вещь' вес 250, 'обувь' вес 80
ответ: Валенок — это обувь (категории: обувь -> вещь).
```

Наивное ранжирование по весу выбрало бы **грубую** «вещь»: coarse-свойства
подтверждаются опытом чаще именно потому, что они coarse (у «вещь» подтверждений
всегда больше, чем у «обувь»). Опасность реальна, но на текущем коде она
спрятана за тем, что вес на выбор не влияет вовсе.

## 9. Тесты: что пинит ранжирование (замер мутацией)

В `_definition_answer` вставлено настоящее ранжирование `hierarchy` по
`observation_weight` — **500 тестов, OK, ни один не покраснел**. Ранжирование
опытом не закреплено ничем: ни разрешено, ни запрещено.

Одновременно существует прямой замок на ту же тему в другом месте:
`tests/test_cortex_experience_contract.py::test_prediction_ignores_synapse_weights`
(предсказание игнорирует веса синапсов) и `test_ontology_weights_survive_many_ticks`
(цикл не имеет права писать в `weight`). Любая правка обязана считаться с ними.

## 10. Что из этого следует (в очередь, не молча)

Проблему «кто лучше» числом опыта **решать нельзя**: п.8 показывает, что частота
подтверждения коррелирует с грубостью, а не с правильностью. Порядок обязан
зависеть от содержания, например:

* близость категории к предмету (длина/специфичность строки — тоже не содержание);
* источник: Вики-категории между собой сопоставимы, пользовательская категория —
  нет (у пользователя их обычно одна, и она выбрана руками);
* явная полнота: `definition` уже выигрывает у всех категорий, это проверенный
  случай (замер 5) — тот же принцип применим и внутри категорий.

Любое из этих правил обязано быть **замеренным**, а не «кажущимся правильным», и
обязано быть записанным в `_definition_answer` комментарием с числом — иначе
следующая сессия примит `h[0]` за случайность и переделает обратно.
